# R147 Automatic ChatGPT-to-Signal-Tower Ingress

R147 is a **transport/orchestration host**, not a new Signal system.

## User-facing contract

The user only needs to express an explicit capture intent such as:

> 把这个录入信号塔

An authorized ChatGPT caller derives a compact **public-safe** request and writes it to the dedicated GitHub transport branch
`signal-tower/ingress` under `transport/requests/<attempt_id>.json`. The user does not construct a Signal envelope, choose a
Ledger/Gateway/Resolver, or supply R145 proof objects.

The GitHub-native ingress then:

1. validates the bounded public-safe request and explicit capture/no-capture semantics;
2. deterministically derives the full R136 envelope and stable logical capture identity;
3. replays the Git transport journal through the **existing canonical S0C `DurableSignalLedger`**;
4. materializes owner-domain evidence through the existing R137/R145 exact-source and semantic-authority path;
5. composes the existing R146 `DurableAdmissionEntrypoint` with the existing S0E gateway, S0C ledger and R145 resolver;
6. performs S0C dedupe/collision handling and R146 same-ledger read-back;
7. rebuilds the complete candidate journal in a **fresh second S0C ledger** and requires identical logical history/projection checksum;
8. only after that fresh replay succeeds, appends the admitted S0C event to the Git replay journal and emits a compact receipt.

## Durable-state rule

`transport/admitted_events.jsonl` is an **append-oriented replay transport only**. It does not become Signal truth and must never be
queried as an independent Signal database. Every invocation starts from a fresh S0C ledger and accepts journal state only after canonical
`DurableSignalLedger.ingest_raw()` replay succeeds. The S0C event model, reducer, idempotency rules, history and projection remain canonical.

This is what makes independent invocations meaningful: process B does not inherit process A's Python objects or temporary SQLite file.
It observes process A only through durable Git state, reconstructs S0C, and then lets canonical S0C/R146 decide whether the new request is
`ADMITTED`, `IDEMPOTENT_DUPLICATE`, or a fail-closed collision.

## Trust and privacy boundaries

- No second Ledger, Gateway, Resolver, Domain Registry, Task, Route, Work Claim or write-authority system is created.
- Caller-supplied fields containing authority/proof/resolver/gateway/ledger/raw/private/credential material are rejected.
- Raw conversation bodies are not a transport field. Only a public-safe summary and structured intent metadata may be committed.
- GitHub Issues, YAML receipts and transport files are evidence/transport. They are never substituted for S0C truth.
- Owner-domain source reads remain read-only. AI Film and other public governed domains are observed through the existing R137/R145 path.
- Private/unavailable owner authority, unknown domains, stale canonical state or source drift fail closed before durable transport append.
- A normal capture does not create a Task, Route, Work Claim or domain write permission.
- The production GitHub Actions job has `contents: write` only on the dedicated ingress job so it can persist the transport journal/receipt.
  Pull-request CI remains `contents: read`.

## ChatGPT transport request

The following is an integration object generated by the authorized ChatGPT caller, **not user-facing boilerplate**:

```json
{
  "schema_version": "R147ChatGPTCaptureRequest/v1",
  "attempt_id": "chatgpt-generated-attempt-id",
  "capture_command": "把这个录入信号塔",
  "source_project": "EUSTIA_AI_FILM",
  "public_safe_summary": "A sanitized public-safe summary of the requested durable intent.",
  "desired_effect": "The intended effect.",
  "problem_to_solve": "The problem this Signal records.",
  "success_condition": "How later evidence can show the desired effect was achieved.",
  "proposed_primary_domain": "AI_FILM_SYSTEM"
}
```

Unknown lists such as risks/assumptions/expected problems are filled as `UNKNOWN` rather than guessed. `attempt_id` is invocation identity, not
Signal identity. In the normal path R147 derives logical Signal identity from the stable semantic intent, so the same request in a later
independent invocation reaches canonical S0C idempotency. `capture_identity` is optional and exists only for an upstream stable message
identity; if it is reused with changed semantics, canonical S0C rejects the collision.

## GitHub-native invocation sequence

After R147 is canonical, an authorized ChatGPT caller performs these connector operations automatically when explicit capture intent is
detected:

1. ensure branch `signal-tower/ingress` exists from current canonical `main`;
2. create exactly one public-safe request file under the R147 `transport/requests/` path;
3. read the workflow-generated receipt under `transport/receipts/<attempt_id>.json`.

No user copy/paste of envelopes, proof objects, CLI commands or workflow inputs is part of the normal path.
