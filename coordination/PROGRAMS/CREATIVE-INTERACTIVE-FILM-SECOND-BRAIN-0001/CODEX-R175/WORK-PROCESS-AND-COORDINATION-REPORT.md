## Difficulty

Actual difficulty: `D4_BOUNDED_SECURITY_AND_FILESYSTEM_SEMANTICS`.

Observable reasons:

- correctness depends on both content identity and filesystem object identity;
- Windows junction/reparse and byte-range lock semantics differ from POSIX;
- the verifier must reason about bounded AST aliases and browser escape forms;
- candidate configuration and workflow must not be able to lower the policy they
  are supposed to enforce;
- exact-head evidence must remain distinct from independent acceptance.

## Plan changes

- The initial Windows lock covered only the current source size. Primary-source
  research showed the protected range can extend beyond EOF, so the implementation
  now locks the supported positive span and tests append denial.
- Initial AST handling focused on named aliases. Adjacent inspection found direct
  dynamic-import return attributes and `__call__` forms, so bounded reference
  resolution was widened.
- Executor verification was initially a manual command sequence. User cost and
  coordination goals justified a B-level one-command runner for Codex/WorkBuddy.
- Product implementation stopped before A1 because R172 owns a potentially
  overlapping session authority; A1 was recorded as a C proposal instead.

## Discoveries

- Byte-range locking only the current length leaves a conceptual append surface.
- A source hard link creates a second path to the same underlying legacy session.
- Candidate scan roots themselves require confinement to avoid repository escape.
- A fake YAML `pull_request` block outside top-level `on` can fool a naive path
  extractor unless hierarchy is checked.
- The current product remains single-script, single-session and director-hardcoded;
  the next valuable product slice is contract and authority work, not more legacy
  CLI branches.
